# Query execution

> **Read when:** working on the query builder, candidate narrowing/intersection, OR clauses, pooled results, or the query-string API.

## Builder & intersection

- `Query()` returns a fluent builder. Each `WithXxx(...)` / `UseIndex(...)` adds a candidate-narrowing lane; the runtime intersects lanes on a **stackalloc bitmap** and short-circuits on the first empty set — no further index walks, no allocations.
- Discriminators gate which operations are callable at compile time: `ExecutableQuery<TCache>` (full surface), `NonExecutableQuery<TCache>` (join filter callbacks — `WithXxx`/`UseIndex`/`Or` only, `Execute*` hidden), `NarrowOnlyQuery<TCache>` (OR branch lambdas — narrowing only). `AsNonExecutable()` (internal) swaps `Executable → NonExecutable` preserving other generics.

## Execution flavors

- `Execute()` — allocating.
- `ExecutePooled()` — returns a disposable `QueryResults<T>` the caller **must `Dispose()`**. Default for hot paths.
- `QueryResults<T>` has a **ref enumerator**: `Enumerator.Current` is `ref T`, so `foreach (ref var x in results)` mutates the backing array in place. `IEnumerator<T>.Current` stays an explicit by-value impl so the interface contract is unchanged.

## Sorted paging — `Sort` vs `SortBounded`

Two plans, chosen by the caller (`IJoinResolver.AllowsBounded`, set by `SortBounded`); never inferred, because they order comparer-equal rows differently.

- `Sort(cmp)` — classic: materialize, full-sort (`QueryResults.Sort` / `ValueDictionary.SortAndCrop` → `StableSort`), slice. **Stable**: comparer-equal rows keep encounter order, the same tie rule the bounded plans apply, so both plans return the same rows for the same query. **0 B/query with a struct comparer** (#77): `StableSort` carries the comparer as a type parameter, by `ref`, through every frame, and sorts a pooled index array for both overloads, then permutes rows (and, keyed, the caller's items) once — the framework's `Span.Sort(keys, items, comparer)` takes `IComparer<TKey>` and boxes a struct (24 B), and its single-span sort builds a `Comparison<T>` over the box on top (88 B). Pinned by `TopKAllocationCoreTests.ClassicSort*`, `StableSortTests.Sort_StructComparer_AllocatesNothing_*` and the `query.sort*.alloc` tripwire metrics at 0. **Index sort on the keyed path too** (#67): sorting the joined rows in place with a Hoare introsort and repairing ties afterwards recursed into every tie run swapping references (a write barrier per swap) and then gathered the result a second time; the index sort halved `query.sortTiedLeftThenJoinClassic.p50` and took 11% off `query.sortTiedJoined.p50`.
- `SortBounded(cmp)` — with a finite `take`, the base walk feeds `TopKSimpleResultContainer` (simple) or `TopKJoinedBaseContainer` (joined, `ExecuteCoreJoinedTop`; the frozen pipeline drives its own `FrozenTopKJoinedContainer` instead — same behaviour, see below), which pick a plan once at `Init(maxCount)`:
  - **heap** while `K = skip + take` is below `maxCount / 4`: pooled max-heap of K rows (`TopKSelect.Push`/`DrainAscending`), O(N log K), buffer of K.
  - **collect + select** otherwise: collect every matched row, `TopKSelect.SelectPage` introselects the page bounds and sorts only the page — O(N + take log take), buffer of N.
  Unbounded `take` and unsupported shapes (comparer over joined fields, post-join sorter, an inner resolver without `SupportsNarrowOnly`) fall back to the classic core.
- **When to use which** — the deciding variable is `take` as a fraction of the matched rows, not `skip`: pages of tens-to-hundreds → `SortBounded` (measured 2.3–8.6× faster; deep pages win too), a quarter or more of the result → `Sort` (bounded is 1.3–2.7× slower there and rents an O(N) buffer). Ties no longer decide it: both plans break ties by encounter order, so the choice is purely about cost.
- **Do not add a "large prefix" fallback** (tried and reverted). Routing a large-`take` page to the classic core to dodge the 1.3–2.7× makes the plan silently return *different rows* whenever the comparer ties — the classic sort does not break ties by encounter order — which breaks the partitioning guarantee `SortBounded` exists to provide. `SortBounded_PagesConcatenateToTheWholeResult` and `EqualSortKeys_PagesCoverEachRowOnce_AcrossSelectionPlans` fail immediately if you try. The caller chose this plan; honouring the choice beats second-guessing it. The near-full-page cost is a documented property, not a defect. (A prefix sweep at N/16…N/2 was also inconclusive on an M4 Pro: ±4.7–13 ms error bars against 1–3 ms differences, non-monotonic — there is no sharp crossover to gate on, just a broad flat band between "clear win" and "clear loss".) If it ever becomes worth it, the safe version needs the caller to declare the comparer total, not a heuristic.
- **Ties**: bounded rows carry their encounter ordinal (`(value, ordinal)` tuples) and `TopKValueComparer` / `TopKPairComparer` break ties by it, so consecutive pages of an unchanged result partition it. With a *total* comparer both plans return identical output.
- **Comparer plumbing — no erasure, no allocation**: the comparer never leaves the resolver. `IJoinResolver.OrdersByLeftValues<TLeft>()` answers the gate without materializing anything (so a fallback pays nothing), and `CompareLeftValues<TLeft>` compares inside the resolver, reinterpreting `TLeft`→`TResult`. The simple container is generic over `TResolver` and holds it by value; the joined one goes through `IResolvers.CompareLeftValues`, forwarded down the chain by a JIT-folded `TResolver.IsSorter` test, with `TopKPairComparer` holding a **pointer** to the chain (it is copied into every sift/partition frame). Result: **0 B/query** on the paged shapes — pinned by `TopKAllocationCoreTests`. The old `TryGetLeftComparer` seam is gone; it boxed struct comparers and built a `Comparison<T>` delegate.
- **Inner joins**: the narrow pass (`UnsafeNarrowIndexedInner`) keeps the right values that passed the filter in a pooled `ValueDictionary` on the resolver; the fill (`UnsafeFillNarrowedInner`) copies them onto the page rows without re-reading the cache or re-running the filter, so a right replaced between the passes cannot surface; `ReleaseNarrowedInner` returns the map from the `finally` (nested, so a throw in one cleanup step cannot strand the next).
- **Phantom rows (fixed)**: `GetCandidates` filters an index-seeded candidate set once before any resolver sees it. It used to hand it over unfiltered while auto-seeded sets *were* filtered, so an inner join retained slots for lefts the `Where` rejects — rows with a default `Left` and `Count > TotalCount`, reachable through plain `Execute()`.
- `TopKSelect` is zero-allocation, reaches elements by reference, and constrains its comparer to `struct` so every instantiation devirtualizes; `ValueDictionary` is fixed-capacity and its insert paths throw on overrun in every build configuration (with the `Debug.Assert` kept for the dev-time break).
- Canonical refs: `benchmarks/Prague.Benchmarks/TopKExecuteBenchmarks.cs` + `RESULTS.MD`, `tests/Prague.Core.Tests/Join/TopK*`, `tests/Prague.Core.Tests/Join/ClassicVsBoundedDifferentialTests.cs`, `tests/Prague.Core.Tests/Collections/TopKSelectTests.cs`.

## OR clause — disjunctive narrowing

- `.Or(b1, b2)` and `.Or(b1, b2, arg)` — UNION-style candidate narrowing. Branch lambdas receive a `NarrowOnlyQuery<TCache>` discriminator.
- Protocol: bitmap mark-and-prune via `IncrementalIntersecter` ([`collections.md`](collections.md)); cross-branch UNION via `BitHelper` SIMD `Vector<int>` ops; survivors pruned by `RetainOnly`. **Cost scales with surviving candidates, not index-result size.** No-op branches (`q => q`) are detected and excluded.
- Works inside `JoinOne` filter callbacks (paired core uses a hybrid: `IncrementalIntersecter` per-branch, `ValueSet` merge cross-branch — pairs dedup by `.Key`). Orchestrated by `IOrCapable` on both the unpaired and paired cores.
- Canonical refs: README "OR Queries", `docs/superpowers/specs/2026-05-19-or-query-clause-design.md`.

## Prepared queries — build once, execute on demand

`src/Prague.Core/QueryBuilders/Prepared/`; design in `docs/superpowers/specs/2026-09-09-prepared-query-command-design.md`.

- **Shape**: a recorder (`PreparedNarrowers<TKey,TValue,TArgs,TChain>`) sits in the left-query slot of the ordinary `CacheQueryBuilderCombined`; each `UseIndex` / `Where` / `Or` / `If` / `Match` appends a `NarrowerLink` at the type level, joins and sorts append the usual resolvers, and `Build()` freezes it into a `PreparedQuery<TArgs,TResult>` (the one allocation). `Execute(in args)` copies the struct, replays the chain into a fresh eager core and runs the eager execution — parity is structural, pinned by `tests/Prague.Core.Tests/Prepared/` (293 differential / allocation / leak / concurrency / frozen tests).
- **Discriminators**: `PreparedQueryDiscriminator<TCache>` (top level: narrow, filter, join, sort, `Build`; no `Execute*`), `PreparedNarrowOnly<TCache>` (`Or` branches: `UseIndex`, nested `Or`, narrow-only `If` / `Match`), `PreparedConditionalBranch<TCache>` (`If`/`IfElse` branches and `Match` arms: `UseIndex`, `Where`, `Or`, nested `If` / `Match`). All are `ICacheCarrier<TCache>`.
- **Carrier rule**: `TCache` is whatever `Prepare` was handed. `cache.Prepare()` / `Prepare<TArgs>()` on a raw `InMemoryDataCache` use the cache itself; the generated wrappers call `Cache.Prepare<XxxCache, TKey, TValue, TArgs>(this)` so `TCache = XxxCache`, which is what the generated `WithXxx` / `JoinWith{T}` constraints (`ICacheCarrier<XxxCache>`) bind on. `Build`, `Sort`, `SortBounded` are generic over `TCache` and read the cache from the recorder.
- **Branch rule**: `Or` / `If` / `IfElse` / `Match` seed their branch builders with the **enclosing** `TCache` and carrier value (`builder._discriminator.Cache`) and the enclosing recorder's cache, so generated narrowing extensions bind inside branches. C# does not infer a type argument from a constraint, so these verbs are overloaded per receiver discriminator (`PreparedQueryDiscriminator<TCache>` / `PreparedNarrowOnly<TCache>` / `PreparedConditionalBranch<TCache>`) and forward to one core each (`OrCore`, `IfCore`, `IfElseCore`, `MatchCore`; seeds in `PreparedBranchSeeds`).
- **`Match`** (`PreparedQueryBuilderMatchExtensions.cs`, `Narrowers.Match.cs`): `.Match(static a => a.Mode, m => m.Case(tag, b => …).Case(…).Default(b => …))` — tag-dispatched recorded arms, the prepared twin of a C# `switch` over type-preserving reassignments. The selector runs per execution (one delegate call); arms run once at build against the same seed builders `If` uses and accumulate as a type chain with no arity limit (`EmptyArms` → `MatchArms<TPrev,TArm,…>` per `Case`, optional `DefaultArm<…>` tail; `Case`/`Default` are extensions on `MatchArmsBuilder<…>` constrained on `IOpenMatchArms`, so a `Case` after `Default` is CS0315). Replay walks arms in declaration order, `EqualityComparer<TTag>.Default.Equals` (JIT-devirtualized for value types; enums do not implement `IEquatable<T>`, hence no constrained call), first hit wins (a duplicate tag resolves to its first arm), else the default, else no-op — so an unmatched `Match` as the first narrower leaves `_first` untouched and the next narrower seeds. `Describe` → `NarrowerKind.Match` with `Value = MatchArmTags` (boxed tags + `HasDefault`) and one child per arm; `FrozenPlanner` always replays it. An opaque per-execution `Eval` callback was considered and rejected: recorded arms keep the plan analyzable.
- **Optional-bounds range** (`PreparedQueryBuilderOptionalRangeExtensions`, `Narrowers.Range.cs`): `UseIndex(rangeIndex, from: Func<TArgs,T?>, to: Func<TArgs,T?>, fromInclusive = true, toInclusive = true)` and the bound `UseIndex(rangeIndex, T? from, T? to, …)` — "from and/or to" in one step, which the type-state `RangeQueryBuilder` cannot spell in one lambda. Replay builds an `OptionalRange<T> : IRangeQueryBuilder<T>` (two `RangeValue`s, `None` for an absent bound) and hands it to the eager `UseIndexCore` through a cached `(rb, range) => range` pass-through. **Both bounds absent never reaches the core**: `UseIndexCore` has no `(None, None)` arm and throws `UnreachableException` on both the plain and the intersecter path (pinned in `PreparedQueryOptionalRangeDifferentialTests`), so the narrower skips the call — the eager query that never called the range, `_first` untouched. Value-type keys (`RangeOptionalArgNarrower`, `Nullable<T>`) and reference-type keys (`RangeOptionalRefArgNarrower`, `T?`) are separate overloads picked by constraint; the bound form is one `RangeOptionalNarrower` for both. Spell at least one literal `null` bound as `(T?)null` in the bound overload, otherwise the two families are ambiguous for a bare `null`.
- **Parameters**: bound values, `Func<TArgs, T>` selectors (static lambdas), `Where(Func<TValue,TArgs,bool>)` through a per-thread pooled predicate box — zero allocation per execution, pinned relative to eager by `PreparedQueryAllocationTests` and `Prague.Generated.Tests/Prepared/PreparedGeneratedAllocationTests`.
- **`BuildFrozen()`** (`FrozenQuery.cs`, `FrozenPlanner`): `Build()` plus a build-time plan. The chain is flattened into `PlanInfo` descriptors (`Explain()` prints ops, executor, active optimizations and their live state) and bound to one of three executors: `PointLookup` (unique-eq + filters: two probes, 0/1 rows, 5–8× eager), `Pipeline` (stage 3 — every other simple plan whose index steps are non-composite, unsorted or under `Sort` / `SortBounded`, and every joined plan of the same steps under a `SortBounded` followed by outer `JoinOne`s; see below) or `Replay` (everything else — composites, unsorted / classic-`Sort` joins, inner joins, `JoinMany`, filter-only, `Pipeline = false`; the stage-1 executor, exactly the `Build()` body, when no optimization applies; the `OptimizedReplay*` twin when a fused filter or hint does). The stage-2 `IndexStepsExecutor` (adaptive intersection) was retired in stage 3 step 3 — the pipeline's seeds cover its two roles. `BuildFrozen(FrozenOptions)` toggles the optimizations; defaults preserve the eager row sequence:
  - **Pipeline executor** (`Pipeline/PipelineExecutor.cs`, `Pipeline/PipelineStep.cs`, `Pipeline/Steps/*`; design `docs/superpowers/specs/2026-09-09-frozen-pipeline-executor-design.md`): the non-composite narrowers implement `IPipelineStepSource` and build one `IPipelineStep` each (boxed once at build). Per execution: every step `Bind`s the arguments once into a type-erased `StepBinding` in a stack `PipelineFrame` (unmanaged index keys ≤ 16 B in two inline slots, reference keys in object slots; larger struct keys replay); a seed is chosen and its keys copied out under one `ReaderGate` pin into `SeedKeys` (256 int keys on the stack, `PragueArrayPool` above; a `PooledSet` bucket is copied by the bulk `PooledSet.CopyKeysTo` — one generation read, one acquire of `LastIndex`, plain loads over the slot array, ~20× the per-slot-volatile enumerator; multi-bucket seeds dedupe through a `ValueSet` exactly as the eager `UnionWith` does). **Seed selection** (design §3.3 / §3.4, `SeedMode`): *fixed* (unsorted `Execute*`) — the **first active** step seeds, so the encounter order is the eager one; when that step is `PooledSet`-backed (list equality, key-set) and another active equality step's live signal is at most half its own (`2 × small ≤ first`), the small step is walked instead, each survivor is located in the first step's set with `PooledSet.TryGetSlot`, and the survivors are sorted by slot (`Span.Sort` on a `(slot, key)` scratch: 256 slots on the stack, the pool above) — the eager sequence at the small step's cost (`list(1k) ∩ list(100)` walks 100 keys, not 1k); *free* (`Count`; classic `Sort`, whose rows are fully sorted afterwards; unsorted `Execute*` under the opt-in `ReorderIndexNarrowers`) — the smallest signal seeds (unique 0/1 always wins; ties → declared order; an exact zero returns empty with no walk; a range / last-updated B+tree estimate replaces an exact count only when `2 × estimate < exact`), and the row order follows the seeding source. A walked step is index-judged; a step whose walk stands in for the first step's (the small step, a moved free seed) keeps its value-side probe on the survivors so the rows it admits are judged by the value returned. `Explain()` prints the seed rule and the last execution's decision (`last seed: step 1 ListEq (signal 6), probe: slot-sorted into step 0 ListEq (signal 34)`; recorded only when the decision changes — no per-execution shared writes); every later step probes each candidate on the key (unique: `TryGetValue` + `Equals`; last-updated: `TryGetLastUpdated`; list/key-set under `IndexSideProbes`) or on the fetched value (list: `KeySelector(value) == k`; range: `KeyOf(value)` against the bounds; key-set: `Matches(value)`), then the top-level filters run directly (`FilterStep`, fused + adaptive order when ≥ 2, no `ArgPredicatePool`), then `SimpleResultContainer` is driven as the eager core drives it (`Init(seedCount)`, `Add`, `Seal`, `BuildResults`) — `TotalCount`, paging, clone timing and pooling are the eager ones. `Count` is the same walk without a container. An empty unique `In` span short-circuits to zero rows; an empty list `In` span or an unbounded optional range is an inactive step; all steps inactive → the store walk. Value-side probes judge a row by the value they return, so under a concurrent writer they never return a row contradicting the query where eager can (design §14.1); `FrozenOptions.IndexSideProbes = true` restores the eager index-side window for list / key-set probes and replays plans with a range probe. `ListRange` (1k bucket ∩ 60k window) drops from ~400 µs to the bucket walk plus one lookup per candidate. Classic `Sort` plans drive `SimpleResultContainer<…, SortResolver>` (the container's `BuildResults` runs `StableSort`, then slices): a total comparer gives the eager sequence byte for byte; with ties, each tie group holds eager's rows but the free seed changes their order inside the group (`context/query.md` "Sorted paging" already leaves classic ties unspecified). **`SortBounded`** (step 6, design §8): the same pass with the **fixed** seed feeds the eager `TopKSimpleResultContainer` behind exactly the eager `ExecuteCoreSimpleTop` gate (`take != int.MaxValue`, non-negative page, a bounded left-value sorter) and the classic container when the gate fails — the bounded container breaks ties by encounter ordinal, and the fixed seed makes those ordinals eager's, so pages are byte-identical with a tie comparer too (`ReorderIndexNarrowers` is the only way to move the seed, as for unsorted plans). A probe-free plan (one active step, direct filters) runs a small `WalkPlain` loop so the container's `Add` chain inlines as it does in the eager store walk. **Joined plans with fused `JoinOne`s** (`Pipeline/PipelineJoinedExecutor.cs`, steps 5–6, design §7): a joined plan takes the pipeline when its narrowing is a pipeline plan, it has no `JoinMany`, at most one sorter, and every join either **fuses** or (only in the `SortBounded` → outer-joins shape) keeps its paired read. A `JoinOne` fuses when its resolver carries no filter callback (`NoFilter`, i.e. `IJoinFilter.IsNoOp`) — all four families, identity or key selector, outer or inner, chained, with one exception: an **inner left-symmetric** join replays by default because its fan-out emits the rows grouped by right key, which a per-left lookup cannot reproduce (opt into the reordered form with `FrozenOptions.FuseSymmetricInnerJoins`, the way `ReorderIndexNarrowers` opts into a moved seed; an *outer* left-symmetric join is unaffected). When a join does fuse, the pipeline does the right lookup itself: `IFusableJoinOne.TryLookupRight` is the resolver's own read chain (PK-to-PK → selector → right store; right-unique → right index → store; left-unique / left-symmetric → the left index's `Reverse` → optional selector / right index → store), so a join costs 1–3 hashes per row instead of a pair-set build plus a paired bulk read. The fill is driven **per resolver, not per row** (`JoinedResultContaier.FillFused` → `IJoinResolver.UnsafeFillFusedRows` over every row in the accessor; the per-row chain walk measured slower than the unfused read, because the chain hop over a generic `TLeft` is a `__Canon` lookup per call). Inner joins: a left without a right is neither emitted nor counted, matching eager's candidate narrowing — the classic flow prunes after the fill and recounts, the bounded flow narrows a pooled `RowBuffer` *before* the heap so the encounter ordinals stay eager's, and `Count` narrows keys only. Flows: **classic** (unsorted, a classic `Sort` anywhere, an unbounded/negative page) fills, then `ExecuteJoins(fusedMask)` runs the sorter, the crop and any unfused resolver; **bounded** (an innermost `SortBounded` over the left value, finite page — the eager `ExecuteCoreJoinedTop` gate) feeds `FrozenTopKJoinedContainer` (step 7, `Pipeline/FrozenTopKJoinedContainer.cs`), materializes the page into `JoinedResultContaier` and fills only those rows. That container is the eager `TopKJoinedBaseContainer` behaviourally — same heap-vs-collect-all plan, encounter ordinals, `Seal` total, `Drain` contract and pooling — but the chain hands it the sorter as a **struct type parameter** through `IResolvers.WithSorter` (a per-link `IsSorter` walk paid once per execution) instead of comparing through `IResolvers.CompareLeftValues`, which is a generic method over a reference `TLeft` and so costs one `__Canon`-shared, non-inlinable hop **per chain link per comparison** (measured on the shapes' own top-k workload: 3.86 µs through the sorter, 4.99 / 7.44 / 9.61 through a 1 / 2 / 3-link chain). The eager container is untouched. Any `JoinMany`, an unfusable or regrouping inner join, or an unfusable join outside the `SortBounded` shape replays. `Explain()` prints `joins: n (fused: f, unfused: u, …)`. Measured: `JoinOne` 1.53×, `InnerJoinOne` 1.91×, two chained 1.66× (`RESULTS.MD` "stage 3, step 5"); after step 7 shape A **3.50×**, shape B **1.89×**, B-range **2.10×** — a joined bounded page now costs what the simple one costs (shape B 17.85 µs against 17.62 for the same narrowing and page without its joins; `RESULTS.MD` "stage 3, step 7"). 0 B per pooled execution and per `Count` on every shape incl. both `list ∩ list` orders, three lists, `Sort`, `SortBounded` pages and the classic fallback, the fused joins (outer, inner, chained, sort-after-join, bounded-inner) and shapes A / B (`FrozenPipelineAllocationTests`); parity in `FrozenPipelineTests` (fixed seed), `FrozenPipelineSeedTests` (small-probe, free seed, `Sort`), `FrozenPipelineSortBoundedTests` (`SortBounded`, simple and joined) and `FrozenPipelineJoinTests` (the fused joins).
  - **Fused filters + adaptive order** (`FusedFilter.cs`, default on for ≥2 top-level `Where`s): one predicate replaces the eager `&&` closure (96 B/exec) and the per-filter predicate boxes (one `RentFused` box per execution, or a cached delegate when every filter is constant); the chain replays through `INarrowerChain.ReplayIndexOnly` so the fused `Where`s run once. Every 256th execution samples calls / rejections / (capped) `Stopwatch` cost per predicate and re-ranks cheap rejectors first, publishing an immutable `int[]` via `Volatile`; the steady state writes nothing shared. Pure predicates → same rows; a non-total predicate (one guarded by an earlier `Where`) needs `AdaptiveFilterOrdering = false`. Branch filters (`If` / `Match`) stay in their sub-chains.
  - **Capacity hints** (`FrozenHints.cs`, default on for equality / membership-seeded plans): the candidate set's high-water mark (`ValueSet.HighWaterMark`) is remembered per plan and the next execution pre-creates `core.Candidates` at that capacity before the replay (`FrozenReplay.PreSize`; the eager core is untouched), so a 1k bucket rents once instead of rehashing 47→…→1597. Plain-int advisory state, capped at 1<<20, shrinks after 8 consecutive executions under half the hint. Range-seeded and composite plans get no hint.
  - **Smallest-signal seeding** (`ReorderIndexNarrowers = true`, opt-in — changes encounter order): the pipeline's free seed for unsorted `Execute*` (above). Same set and `Count` as eager; row order follows the seeding source. (Stage 2's `AdaptiveIntersection` option and `IndexStepsExecutor` are gone: with the pipeline there is no candidate set to intersect.)
